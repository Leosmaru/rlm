## Философия (ядро RLM)

**Три раздельные системы, не одна.** SW сливает лорбук+режиссуру в один движок; RLM разводит на три с одной ролью у каждой:

- **`Лорбук`** — *знание о мире* (статика, пишет человек). Приходит с карточкой (`character_book`).
- **`Душа`** — *память/психология* (рантайм, пишет ИИ в MD). **Только личная**, на конкретный чат — не шарится, в карточку не едет.
- **`Режиссёр`** — *события сцены* («сейчас происходит X, реагируй»). **Чисто RLM-фишка.**

**Режиссёр декуплирован от персонажа:**
- Персонаж входит **только со знанием** (лорбук). Событий не несёт — концепции «события лорбука» в экосистеме **нет вообще**.
- Режиссёр **не наполняется из карточки** (ни импорт, ни экспорт), живёт в RLM сам и режиссирует **любого** загруженного персонажа.
- «Событий из чужой книги» не выхватываем — их не бывает.

**ST-совместимая база + опциональные слои.** База RLM = классический ST. Все три усиления — опциональны, по правилу нод №3 `node-logic` («нет ноды/провода → дефолт»):
- `Режиссёр` не подключён → нет событий → ST.
- `Душа` не подключена → нет памяти сверх контекста → ST.
- `Эмбеддер` не подключён → нет semantic, только keyword → ST.
- → Хочешь ваниль — не подключаешь лишнего. Хочешь глубину — доклеиваешь слои нодами.

**Транспорт vs системы.** На диске и в шаринге `character_book` остаётся **чистым знанием** (портируемость цела); разделение на системы — **внутреннее**, происходит на импорте. Наивный персонаж приносит только знание — режиссуру и память RLM накидывает сам, поверх.

## 1. Система `Лорбук` — scope и типы записей

**Три scope (как в ST), раздельные слоты, активны разом:**
- `мир` — глобальный лорбук (`worlds/*.json`), знание сеттинга, общий/переиспользуемый, ничей.
- `персонаж` — `character_book`, знание про персонажа, едет в карточке.
- `чат` — `chat_metadata`, знание этого разговора (стабильные заметки к чату).

Не смешиваются: лор персонажа **не** пихаем в мировой (разный scope + ломает портируемость). Память чата — это **НЕ** чат-лорбук, а `Душа` (§4): чат-лорбук = медленные структурные записи, Душа = быстрая динамичная MD-память.

**Типы записей.** Главный переключатель записи — `trigger_type`. Он решает, какая группа полей смотрится.

| Тип | Когда срабатывает | Новое для ST? |
|---|---|---|
| `keyword` | ключевое слово всплыло в тексте | нет (база ST) |
| `always_on` | всегда | нет (ST `constant`) |
| `semantic` | смысл сцены близок к **фразе-эталону** (векторы, стиль SW) | ≈ (точнее, задаёшь смысл сам) |
| `vectorized` | смысл сцены близок к **тексту самой записи** (векторы, стиль ST) | **да** (ST `vectorized`, «неточная») |
| `range` | номер сообщения попал в окно `min…max` (акт) | **да** |
| `random` | случайно (простой шанс каждый ход) | почти (ST `probability`) |
| `chain` | после срабатывания записи-предка + пауза | **да** |

> В UI типы **разведены** (✅ реализовано): `Лорбук` показывает знаниевые `keyword`/`semantic`/`vectorized`/`always_on` (про тему), `Режиссёр` — событийные `range`/`random`/`chain` (про время). Два «смысловых» режима у лорбука — **разные**: `semantic` (SW) сверяет сцену с твоей **фразой-эталоном** (точнее); `vectorized` (ST) — с **текстом самой записи**, без фразы («неточная векторизация»). Оба на векторах (нужен `Эмбеддер`). Движок (`loreText`) один общий.

**Отдельная ось — как вставляем (`injection`):**
- `lore` — тихо в фон как знание (блок `[WORLD LORE]`).
- `event` — как приказ «происходит сейчас, реагируй». Это уже территория `Режиссёра` (см. ниже).

## 2. Объединённая схема записи лорбука (ST база + добавки SW)

Псевдо-JSON, комментарии = пометка происхождения: `[ST]` / `[SW]` / `[merge]`.

```jsonc
{
  // ─ Идентичность ─
  "uid": 4,                       // [merge] id (нужен для chain)
  "name": "Падение столицы",      // [merge] ST comment ⇄ SW entry_name
  "enabled": true,                // [merge] ST disable(инв.) ⇄ SW enabled
  "content": "Столица пала под…", // [merge] вставляемый текст

  // ─ ГЛАВНЫЙ ПЕРЕКЛЮЧАТЕЛЬ ─
  "trigger_type": "keyword",      // [SW] keyword|semantic|always_on|range|random|chain

  // ─ keyword (старые поля ST) ─
  "key": ["столица"],             // [ST] основные ключи
  "keysecondary": ["осада"],      // [ST] вторичные ключи
  "selective_logic": "AND_ANY",   // [ST] AND_ANY|AND_ALL|NOT_ALL|NOT_ANY
  "exclude_key": ["сон", "миф"],  // [SW] стоп-слова (открытый вопрос №2)
  "case_sensitive": false,        // [ST]
  "match_whole_words": true,      // [ST]

  // ─ semantic ─
  "semantic_trigger": "разговор о войне", // [SW] фраза-эталон смысла
  "semantic_threshold": 0.72,     // [SW] порог близости

  // ─ range ─
  "min_msg": 10, "max_msg": 20,   // [SW] окно номеров сообщений (0 = до конца)

  // ─ chain ─
  "depends_on": 3,                // [SW] uid предка
  "chain_delay": 2,               // [SW] через N сообщений после предка

  // ─ КУДА / КАК ─
  "injection": "lore",            // [merge] lore | event
  "position": "atDepth",          // [ST] для lore: before/after char, atDepth, AN/EM…
  "depth": 4, "role": "system",   // [ST] для atDepth
  "order": 100,                   // [ST] сортировка вставки

  // ─ Тайминги (общие) ─
  "probability": 100,             // [ST] шанс, %
  "sticky": 3, "cooldown": 2, "delay": 0, // [merge] держать / пауза / не раньше

  // ─ Рекурсия (ветка ST) ─
  "exclude_recursion": false,     // [ST]
  "prevent_recursion": false      // [ST]
}
```

Обёртка книги: `name`, `scan_depth` (ST scanDepth ⇄ SW n_depth), `token_budget` [ST], `recursive` [ST], `entries[]`.

## 3. Система `Режиссёр` — лорбук событий (✅ БАЗА РЕАЛИЗОВАНА)

Своя RLM-система, «лорбук, но записи — события, а не знание». Что решено и сделано:
- **Отдельная система**, декуплирована от персонажа (см. Философию). Своё хранилище, **не** `character_book`, **не** `MEMORY.md`.
- **Опциональна:** не подключена нода → событий нет → ST.
- Вставка = режим `event` («происходит сейчас, реагируй»).
- **Полностью автоматический**, как обычный лорбук: записи с триггерами срабатывают **по правилам** и вставляют **готовый, заранее написанный** текст события. **ИИ не нужен, генерации нет.**
- ✅ **Реализовано:** нода `Режиссёр` = **рабочее мини-приложение**, переиспузует движок записей лорбука (общий билдер `buildLoreApp`) с `injection: event` по умолчанию и **тремя триггерами времени** — `range` / `random` / `chain` (см. §Решено; факт-«как есть» — в `architecture.md`).
- Реактивные `keyword`/`semantic` в Режиссёре пока **намеренно не даём** (это епархия Лорбука) — при желании добавить их в список триггеров тривиально.

**Открыто (не торопимся):**
- Наполнение самими событиями (контент, помимо демо-посева) — **позже.**
- Надстройки (последовательности/состояние/условия сверх `chain`) — **позже.**
- **Базовые события** (глобальная библиотека + кастом-оверлей) — **ПАРКОВАНО.**

## 4. Система `Душа` — память (✅ UI-каркас, движок памяти позже)

MD-память в стиле SW Soul Memory / плагина `soul-md`: рантайм, пишет ИИ, **только личная** (на чат), в карточку не едет, общей базы не бывает. Потребитель `Эмбеддера` (RAG).

**✅ UI-каркас сделан:** нода `Душа` из заглушки → **список доков; у КАЖДОГО дока свой вход-коннектор** (по аналогии с плашками комплитера). В коннектор цепляется **обычная нода `Систем промт`** с инструкцией «что и как писать в этот док» — свою ноду под промты **не плодим** (`Систем промт` универсальна). Доки трёх видов (из логики soul-md): **дневник** (дописывание), **трекер** (перезапись на месте), **тема** (RAG); у каждого — понятное русское имя + строка-описание + видимое пояснение вида. Дефолтные доки (Дневник/Статус/Мир/Психика/Темы) только **выключаются**, свои добавленные — **удаляются**. Факт-«как есть» — в `architecture.md`/`node-logic.md`/`formats.md`.

**✅ Промты доков написаны и подключены (пресет).** Синтез из реальных агентов памяти референсов:

| Референс | Модель памяти | Что даёт нашим докам |
|---|---|---|
| **MachineMechanic** (`SillyTavern-MemoryBooks`) | **сцена → запись лорбука** `{title, content, keywords}` (15–30 ключей), поиск по ключам/векторам; ретроспективный архив сцен, неизменяемый | стиль **Темы/Дневник** (сжать факты, ключи для поиска) |
| **Soul of Waifu** (`soul_memory.py`, `prompt_engine.py`) | **живая память из агентов:** Router → психология+профиль юзера (MEMORY/USER.md), Archivist → темы (RAG, <300 слов), Diary → тайный дневник от 1-го лица, State-summary → трекеры `[СОСТОЯНИЕ]/[ОТНОШЕНИЯ]/[СЦЕНА]/[ЛОР]/[СОБЫТИЯ]` (наст. время, перезапись) | стиль **Дневник** (SW Diary), **Статус/Мир** (SW state-summary), **Психика** (SW Router), **Темы** (SW Archivist) |

Итог: `Дневник`←SW Diary; `Статус`←SW `[CHARACTER STATES]/[CURRENT SCENE]`; `Мир`←SW `[KEY DISCOVERIES & LORE]`; `Психика`←SW Router (эмоция+сила, напряжение, скрытая цель, доверие, распад эмоций); `Темы`←SW Archivist + ключи MemoryBooks. Тексты — в `SOUL_DOCS[].prompt`.

**✅ Вектор-бэкенд + RAG-чтение сделаны** (2026-08-11): родной эмбеддер ST на многоязычной `multilingual-e5-small`, маршруты `/api/rlm/soul/{chats,all,diary,topics}` (до CSRF), дневник отбирается **семантическим RAG как в SW** (top-k + обрезка). У ноды `Душа` — **вьюер реальных записей** с диска + строка смыслового поиска (живьём зовёт эмбеддер). Факт-«как есть» — в `architecture.md`.

**✅ Движок памяти сделан целиком** (2026-08-11): ЗАПИСЬ — `updateMemory` (кнопка + авто раз в `batch`) заставляет ИИ по инструкциям доков вести дневник (append) / трекеры (перезапись, с чтением прошлой версии) / темы (Archivist); ПОДМЕШИВАНИЕ — `refreshSoulMemory` перед генерацией кладёт `[ПАМЯТЬ ПЕРСОНАЖА]` в плашку «Память». Каждый чат — своя папка (`_chatId`). Semantic/vectorized-лорбук — на настоящих векторах (`/score`). Живой цикл записи требует ключа API у пользователя. Факт-«как есть» — в `architecture.md`.

**Осталось по памяти:** эффективность (кэш векторов вместо пересчёта на каждый запрос), тонкая настройка порогов/промтов на реальных диалогах.

**Душа ≠ чат-лорбук.** Оба про конкретный чат, но разной природы:

| | Лорбук чата | Душа |
|---|---|---|
| Что | стабильные факты/заметки чата | летопись + состояние, поток |
| Формат | записи (ключ→контент) | MD-файлы |
| Темп | медленный, ручной/редкий | быстрый, авто, ~каждый ход |
| Поиск | по триггерам | RAG (постоянная ре-векторизация) |

Причина раздельности: память обновляется слишком стремительно для лорбук-файла и постоянно ре-векторизуется → ей место в динамичных MD, а не в записях лорбука. Подробный формат — в `formats.md`/`architecture.md` по мере реализации.

## 5. Нода `Эмбеддер` (сервис смыслового поиска)

**Отдельная нода, НЕ настройка внутри лорбука.** Причина: векторизация — **общий сервис на несколько потребителей** (см. §8), прятать её внутрь одного из них нельзя.

- **Связь — боковой сервисный вход** (как `Опции` → `API`, правило №3 `node-logic`). Нет подключённого `Эмбеддера` → `semantic`/RAG выключены.
- **Один `Эмбеддер` может кормить всех** потребителей сразу.
- **Модель — свойство ноды** (дропдаун, §6). Сменил на ноде → сменилось у всех подключённых.
- **Нод `Эмбеддер` можно ставить несколько** ✅ — каждая со своей моделью и своим хранилищем.
- **Правило совместимости:** векторы разных моделей несравнимы (размерность 384/768/1024) → потребители одного хранилища сидят на **одном** `Эмбеддере`. Разные модели = разные ноды + разные хранилища.
- **Загрузка модели — одна на модель (не на ноду).** Модель в памяти дорогая (30–500 МБ). Две ноды с **одинаковой** моделью делят **один загруженный экземпляр** (грузим один раз по id модели), но **хранилища/индексы у них раздельные** (по ноде). Практика: нужна одна модель нескольким потребителям → **одна нода + много проводов** (§«Один Эмбеддер кормит всех»); несколько нод — под **разные** модели. Две ноды с одинаковой моделью — избыточно.
- **Разные модели одновременно — штатно:** нода A (модель X) и нода B (модель Y) работают параллельно, обе модели в памяти, каждая кормит своих потребителей. Один потребитель = один `Эмбеддер`; перецепил хранилищного потребителя (`Душа`) на другую модель → **авто-перевекторизация** (§7). У `semantic`-лорбука хранилища нет → перецепляется свободно.
- **Устав нод соблюдён:** эмбеддер реально работает в бэкенде (RAG `soul-md`) → нода = «видимая ручка настоящего куска».
- **Название:** нода зовётся **`Эмбеддер`** (не «векторизатор»/«трансформер» — эмбеддер = точный термин «текст → вектор»).

## 7. Ре-векторизация при смене модели

При подключении **другого** `Эмбеддера` (или смене модели на той же ноде) у потребителя с хранилищем:

1. **Проверка = сравнение «отпечатка модели»** (id + размерность), хранимого рядом с индексом. Совпал → ничего; не совпал → шаги 2–3.
2. **Снести старые векторы** этого хранилища.
3. **Авто-перевекторизация** — автоматически, **фоном, с прогрессом** (на телефоне долгий ре-эмбеддинг — UI не вешать).

- Перестройка **обязательна:** разные модели дают разную размерность (384/768/1024) → старые векторы структурно несовместимы.
- **Только для хранилищных потребителей** (`Душа` soul-md RAG). У on-the-fly `semantic` векторов нет → проверка пропускается.
- **Свап-стратегия — только пересчёт из текста** (текст всегда на диске → точно и дёшево). Параллельные индексы и alignment — **отклонены** (память / точность).

## 8. Потребители `Эмбеддера`

| Потребитель | Хранилище | Ре-векторизация при смене |
|---|---|---|
| `semantic`-лорбук | **нет** (считает на лету, кэш в ОЗУ) | не нужна |
| `Душа` `soul-md` (RAG) | есть (индекс на диске) | да (§7) |

**НЕ потребители:** `keyword`-лорбуки (в т.ч. лорбук чата) и референс-плагин `MachineMechanic` отбирают по **ключевым словам** — эмбеддинги им не нужны, к `Эмбеддеру` не подключаются.

## 9. Подключение нод на холсте

Все источники → **`Промт комплитер`** (контент), каждый в свою плашку. `Эмбеддер` — боковой сервисный вход (как `Опции` → `API`).

Каждый scope лорбука — **своя плашка** (в ST это один слитый конвейер World Info с позицией на запись; у нас три явных входа по scope, см. `backend-research.md` §8).

| Источник | Куда / плашка | К `Эмбеддеру`? |
|---|---|---|
| Лорбук мира | комплитер → плашка **«World Info»** | да, если `semantic` |
| Лорбук персонажа | комплитер → плашка **«Лорбук персонажа»** | да, если `semantic` |
| Лорбук чата | комплитер → плашка **«Лорбук чата»** | да, если `semantic` |
| Душа | комплитер → плашка «Память» | **да** (RAG) |
| Режиссёр | комплитер → плашка «События», `In-chat @1` | нет |

```
Источники ─────────▶ Промт комплитер ──▶ API ──▶ Чат
Эмбеддер ─(боковой)▶ Лорбук(semantic) / Душа(RAG)
Опции ────(боковой)▶ API
```

**Базовый пресет ✅ реализовано (заглушки):** `buildDefaultPreset` создаёт и подключает `Эмбеддер` + **три ноды `Лорбук`** («Лорбук мира» → «World Info», «Лорбук персонажа» → «Лорбук персонажа», «Лорбук чата» → «Лорбук чата») + `Душа` (→ «Память») + `Режиссёр` (→ «События»); `Эмбеддер` → боковой вход всех трёх лорбуков + Души; плюс `Персонаж → Лорбук персонажа`. Проверено: 11 нод, 17 проводов. Тела `Лорбук`/`Режиссёр` уже рабочие (см. «Решено»); `Душа`/векторный бэкенд `Эмбеддера` — позже. Детали UI — в `app-guide.md`, история — в `changelog.md`.

## Открытые вопросы

**⏸ ПАРКОВАНО (задел, не сейчас) — имитация ST-outlet через мульти-выход лорбука.** Идея (пользователь): дать ноде `Лорбук` **несколько отдельных выходов** в разные плашки, и у КАЖДОЙ записи — выбор «в какой выход». Это даст per-entry placement = имитацию ST-outlet (позиция №7) на нодовой модели RLM, без числа-позиции. Почему не сейчас: outlet — редкая продвинутая фича (в плагине по умолчанию не используется), а текущий fan-out одного выхода **копирует записи во ВСЕ** приёмники (не «каждая в свою») → нужна новая механика (несколько именованных выходов + пер-запись селектор). `Хронике` не нужно (все главы в одну плашку «Лорбук чата»). Вернуться при реальном кейсе «эту запись — в другое место».

**⏸ ОТЛОЖЕННЫЙ ЗАХОД — рекурсия лорбука (делать ПАКЕТОМ).** ST-рекурсия World Info: вставленный текст записи **пере-сканируется** → тянет связанные записи (сказал «Эльдор» → подтянулись «король», «драконы»). Делать РАЗОМ: много-проходный скан + **потолок глубины** (анти-зацикливание) + флаги `preventRecursion` (мой текст не активирует других) и `delayUntilRecursion` (запись всплывает ТОЛЬКО если её позвали рекурсией, не из чата). Не срочно: у нас `semantic`/`vectorized` триггеры **частично закрывают** «связанное всплывает» по смыслу (близкая по эмбеддингу запись всплывёт и без буквального ключа). Трогает ядро `loreText` (все лорбуки). Решение (пользователь 2026-08-13): **паркуем**, поднимаем отдельным заходом по `Лорбуку` целиком.

**⏸ К ДОРЕШЕНИЮ ПОЗЖЕ (рядом с outlet) — `order` = ОДИН рычаг на ДВЕ задачи.** Сейчас `order` решает сразу: **(а)** приоритет при бюджете токенов (кого срезать первым) и **(б)** позицию записи ВНУТРИ блока (выше `order` = выше в блоке, `candidates.sort((a,b)=>b.order-a.order)`). Развести нельзя без правки **общего** движка лорбука. **Пока решили ОСТАВИТЬ один рычаг:** для блока авто-сводок расстановка внутри блока влияет мало, а «силу» (recency) рулим **положением плашки** «Лорбук чата», не `order`. Если на реальных диалогах расстановка внутри начнёт мешать — развести на два ключа: `важность` (только бюджет) + `порядок` (только расстановка).


**✅ Темы = Лорбук? — РЕШЕНО: НЕТ, раздельно** (пользователь, 2026-08-11). Механика отбора у `Темы` совпадает с vectorized-лорбуком (движок один), но это **разные системы по сути**: лорбук — авторское знание (человек, едет в карточке, шарится), темы — рантайм-**память** ИИ (на чат, не шарится, ре-векторизуется). ## Решено (не переспоривать)

- ✅ **Три раздельные системы:** `Лорбук` (знание) / `Душа` (память) / `Режиссёр` (события). Не слитно, как у SW.
- ✅ **Режиссёр — чисто RLM, декуплирован от персонажа:** события не приходят и не уходят с карточкой, концепции в экосистеме нет.
- ✅ **Душа — только личная** (на чат), в карточку не едет, общей базы не бывает.
- ✅ **Три scope лорбука** (мир / персонаж / чат) — как в ST, раздельные слоты, не смешиваются. **Чат-лорбук остаётся** (структурные заметки к чату) и **не равен `Душе`** (динамичная MD-память).
- ✅ **ST-совместимая база + опциональные слои:** не подключил ноду (`Режиссёр`/`Душа`/`Эмбеддер`) → работает как ST.
- ✅ **Транспорт цел:** `character_book` остаётся чистым знанием; разделение систем — внутреннее, на импорте.
- ✅ Нода зовётся **`Эмбеддер`**, отдельная нода, не настройка лорбука; можно **несколько**.
- ✅ **Эмбеддер: модель грузится один раз на модель** (не на ноду) — две ноды с одинаковой моделью делят загруженный экземпляр, хранилища раздельные; для одной модели правильно **одна нода + много проводов**, несколько нод — под **разные** модели. Один потребитель = один Эмбеддер (векторы моделей несравнимы).
- ✅ Дефолтная модель — **`multilingual-e5-small`**.
- ✅ **Ре-векторизация при смене модели**: отпечаток → снос → авто-фон-перестройка; только хранилищные потребители.
- ✅ **Свап-стратегия = только пересчёт из текста** (параллельные индексы и alignment отклонены).
- ✅ **Движок лорбука — матчинг реализован** (`loreText`): вторичные ключи + логика И/НЕ, целое слово, регистр, вероятность; импорт ST-полей. Стоп-слова закрыты в пользу **ST-логики NOT** (не отдельное `exclude_key`). Позиция записи — **решена по модели SW**: позицию держит **плашка** (scope), у записи только «инъекция» знание/событие; per-entry позиции/порядка ST не тянем (роль «часть вверх / часть на глубину» играет разделение Лорбук/Режиссёр). **✅ Бюджет токенов — реализован по модели ST** (2026-08-11): приоритет по `order` (убыв.), лимит «% от контекста» (дефолт 25% от «Опций»), `ignoreBudget` у записи, overflow-пометка «…+N срезано»; токены — оценка (без токенайзера). Отложено (инвазивно): тайминги (sticky/cooldown/delay), рекурсия.
- ✅ **Движки `range` / `random` / `chain` — реализованы** в общем `loreText`: `range` = номер сообщения в окне `[min..max]` (0=до конца); `random` = **простой шанс/ход** (из «Вероятность,%», без накопителя); `chain` = после срабатывания предка + пауза, **одноразово** (память `el._fired` с якорем на первое срабатывание). `semantic`/`vectorized` **работают на векторах** (эмбеддер ST через `/score`), срабатывают по порогу при подключённом `Эмбеддере`.
- ✅ **`Режиссёр` — рабочее мини-приложение** (не заглушка): общий движок записей (`buildLoreApp`, классы `node-lore node-director`), `injection: event`, триггеры `range/random/chain`, демо-посев событий.
- ✅ **Чистое деление триггеров 3+3:** `Лорбук` предлагает только **знаниевые** `keyword`/`semantic`/`always_on` (про тему), `Режиссёр` — только **событийные** `range`/`random`/`chain` (про время). Движок один общий; ограничение — в списке типов ноды. (`random` для знания бессмыслен, `chain`/`range` — сценарий во времени = события.)
- ✅ **Дальность сканирования реализована:** движок берёт последние N сообщений (0 = все), `always_on` игнорирует; `loreText` принимает список сообщений (`node._msgs`).
- ✅ **Нода `Лорбук` — двухпанельное мини-приложение** (список+редактор, модель в JS) + **полный экран** через глазок (оверлей с топ-баром «← Назад»). Реализовано, см. `app-guide.md`/`changelog.md`.
- ✅ **Подключение:** все источники → `Промт комплитер` (своя плашка у каждого); `Эмбеддер` — боковой к `Лорбук`(semantic)/`Душа`(RAG); `Режиссёр` — плашка «События» `In-chat @1`.
- ✅ **`Душа` = список доков; у каждого свой вход-коннектор** (как плашки комплитера); инструкцию по доку несёт подключённая **обычная нода `Систем промт`**. Отдельную ноду под промты **НЕ плодим** — `Систем промт` универсальна (решение по фидбеку: «нет смысла плодить ноды с одинаковой функцией»). Доки трёх видов из soul-md (дневник/трекер/тема), русские имена + описание + пояснение вида; дефолтные выключаются, свои удаляются. Движок записи памяти — позже (с вектор-бэкендом `Эмбеддера`).
- ✅ **Дневник в контекст — по модели SW (RAG), а не целиком** (выбор пользователя 2026-08-11): запрос и записи эмбеддятся, берётся top-k по смыслу + обрезка «хвостом». Файл-`.md` может расти — в промт идёт только горстка релевантных кусков. Реализовано в `/api/rlm/soul/diary`.
- ✅ **Базовый пресет** включает `Душа` + по ноде `Систем промт` на каждый док (подпись «Промт: <док>», текст-инструкция из SW/MemoryBooks), провод в коннектор дока (`doc:<id>`). Вид дока — кастомный дропдаун `describedDropdown` (описание под каждой опцией).
- ✅ **Терминология:** «World Info» = лорбук **мира** (имя движка/файла ST). Лорбук **чата** — отдельный слот, **не** «World Info». `MachineMechanic` пишет память в **лорбук чата** по ключам — не через `Эмбеддер`; RLM `Душа` = MD+RAG, другой путь.

## Консолидация / уровни (свёртка Хроники) — реализовано 2026-08-15

**Идея (ref: MemoryBooks/MachineMechanic):** записи `Хроники` в «Лорбук чата» сворачиваются снизу вверх по уровням — **Сцена(0) → Арка(1) → Глава(2) → Книга(3) → Легенда(4) → Сага(5) → Эпос(6)**. Накопилось ≥N записей уровня K → модель сжимает их в одну запись уровня K+1, а дети **прячутся** (их «представляет» сводка). Каскад до эпоса. Это **надстройка-бухгалтерия над лорбуком**, не отдельный движок памяти (как и плагин сидит на родном лорбуке ST). Душу **не трогает** (трекеры/дневник — её слой; консолидация только для архива Хроники).

- ✅ **Поля записи лорбука:** `tier` (0=Сцена), `members` (id свёрнутых детей), `hiddenBy` (id сводки, что скрыла запись). Сериализуются/нормализуются сами (`loreNormEntry`).
- ✅ **Движок `loreText`:** запись с `hiddenBy` не срабатывает (не в промт, не в отбор для свёртки).
- ✅ **Вьювер лорбука:** скрытые дети **не в списке** и не в счётчике; у сводок — **значок уровня** (Арка/Глава/…). В «Оглавлении» скрытые тоже не показываются, у пункта — метка уровня.
- ✅ **Нода `Хроника` — секция «Консолидация»:** галка «Авто-консолидация», «сворачивать по N» (дефолт 5), кнопка «🗂 Свернуть сейчас». Авто-триггер — после записи сцены (если галка вкл). Промт консолидации возвращает `{summaries:[{title,summary,keywords,member_ids}],unassigned}`; несшитое остаётся живой записью. Сводки ищутся по **ключам** (работает без Эмбеддера). Пачка — до 12 записей за запрос.
- ✅ **Переименование:** базовая запись Хроники теперь **«Сцена»** (была «глава»), чтобы «глава» встала на свой уровень (2) как в задумке плагина. Затронуты тосты/превью/оглавление/кнопка «Собрать сцену».

**Открытый вопрос (решить позже) — отображение скрытых детей.** Сейчас свёрнутые записи `hiddenBy` **полностью исчезают из виду** (списка/оглавления) — формально остаются в лорбуке. Надо додумать UX: показывать ли их (свёрнутыми под сводкой / отдельным «показать скрытые» тумблером / деревом уровней), можно ли **развернуть** сводку обратно (unfold), и как редактировать. Пока — просто скрыты.

**Возможное развитие (не делаем сейчас):** сделать движок консолидации чуть общее, чтобы **дневник Души** тоже умел сворачиваться по тем же уровням (сейчас — только лорбук Хроники).

## Будущие разработки — клипы (✂ Clip), отложено 2026-09-04

Сам клип реализован: выделил кусок в чате → окно (текст, куда, заголовок, режим всплытия, фраза/ключи,
RU/EN у полей) → запись в «Лорбук чата», куски копятся между маркерами `=== Заголовок ===` … `=== END ===`.
Ниже — то, что есть у MachineMechanic и чего у нас пока нет. **Не делаем сейчас, вернуться по слову.**

1. **«Сжать запись» (Compaction).** Жмёт содержимое ОДНОЙ записи — накопленный внутри список пунктов.
   Правила их промта: сохранить факты, предпочтения, отношения, имена, незакрытые нити, обещания, секреты,
   ограничения; выбросить повторы и воду; склеить пересекающиеся пункты; не добавлять новых фактов; не менять
   имена, местоимения и макросы; **маркеры-обёртки вернуть в точности** (иначе следующий клип не найдёт, куда
   дописывать); вернуть только содержимое. У них промт редактируемый и может ходить своим профилем подключения
   (жать дешёвой моделью, не той, что ведёт игру) — нам это ложится на отдельную ноду API/строку таблицы токенов.

2. **«Пересобрать по теме» (Topical Clip).** Собирает запись по ОДНОЙ теме из набора кусков: раскладка
   **по под-темам, а не по хронологии**, каждый факт самостоятельный; при обновлении «не регрессировать» —
   результат обязан быть полезнее прежнего; **конфликты помечать явно** («в одном месте X, в другом Y»),
   а не выбирать молча; при нехватке данных вернуть маркер `[INSUFFICIENT DATA: …]`. Это ближе к тому, что нужно
   правилам процесса (этапы, договорённости), чем обычное сжатие.

3. **Предупреждение о длине в окне клипа.** Показывать длину будущей записи и её долю от бюджета лорбука
   (у нас бюджет = «% от контекста», по умолчанию 25%), краснеть при переваливании за половину. Причина:
   в `loreText` при переполнении срезается **всё** после первой не влезшей записи («…+N срезано бюджетом»),
   поэтому одна раздутая запись утаскивает за собой остальные.
