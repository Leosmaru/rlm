# RLM — Логика нод (как SillyTavern ложится на узлы)

> **Устав документа**
> - **Зачем:** зафиксировать, как реальный конвейер SillyTavern отображается узлами RLM. Эталон, с которым **сверяемся** при добавлении/правке нод.
> - **Что сюда пишем:** соответствие «понятие ST → нода», что течёт по проводам, правила визуализации.
> - **Чего НЕ пишем:** детали кода (это `architecture.md`), историю правок (это `changelog.md`), разбор «почему так решили» (это `decisions.md`).
> - **Правило ведения:** обновляется, когда меняется само отображение ST в нодах (новая нода / новый вид связи). Всегда «как есть сейчас».

## Главный принцип

Мы **не придумываем свою логику** там, где зеркалим ST. Берём реальный механизм SillyTavern и **показываем его узлами**. Нода — это **видимая ручка** настоящего куска ST.

**Уточнение — RLM-слои (сверх ST).** База RLM = классический ST. Поверх неё есть **опциональные RLM-слои**, которых в ST нет как нод: `Душа` (память MD+RAG, идея SW soul-md), `Режиссёр` (события сцены — RLM-фишка), `Эмбеддер` (смысловой поиск). Они **опциональны по правилу №3**: не подключил ноду → работает как чистый ST. Философия и решения — в `plan-lorebook-vector.md`.

## Два разных потока: ЧТО и КАК

- **Промт** (`messages`) — это **ЧТО** модель читает: контент (персонаж, лорбук, история, системные инструкции).
- **Сэмплеры** (нода `Опции`: температура, top_p/top_k, max_tokens, штрафы, seed) — это **КАК** модель выбирает следующее слово: математика на её выходе.

Это разные вещи, и в тексте промта они **не смешиваются**. В запросе к провайдеру лежат **рядом**, отдельными полями:

```
POST {base}/chat/completions
{ model, messages: [ …собранный промт… ], temperature, top_p, max_tokens, … }
                    └── от «Промт комплитера»    └────── от «Опций» ──────┘
```

## Где происходит склейка

Только в **момент звонка провайдеру** — это нода **API**. Раньше единого «запроса» не существует (промт и настройки живут в разных нодах), позже он уже улетел к модели. Технически финальная сборка тела — в серверном маршруте `server/src/endpoints/rlm.js` (`{ model, messages, ...params }`); нода `API` на холсте — её **лицо**.

## Карта: понятие ST → нода

| SillyTavern | Нода RLM | Что на выходе |
|---|---|---|
| Prompt Manager (Chat Completion) | **Промт комплитер** | собранный промт (`messages`) |
| *(RLM-слой, групповой чат)* | **Мультиплей-комплитер** | вариант комплитера для группы: **слот = тип плашки** (пачка перса, коннекторы внутри — свёрнут = разъём, раскрыт = поля); активный «на передаче» = полная карточка, остальные = «фантом»; слот-**рассказчик** всевидящий (все карточки). Ранжиратор (в чате) двигает «коробку передач». Детали/чек-поинт — `plan-group-chat.md` |
| Карточка персонажа (V1/V2/V3) | **Персонаж** | поля карточки → в плашки комплитера |
| Персона пользователя (User Persona) | **Персона** | имя + аватар + описание → плашка «Описание персоны» |
| World Info / лорбук (3 scope) | **Лорбук** (×N) | записи → плашки «World Info» / «Лорбук персонажа» / «Лорбук чата» |
| Настройки сэмплеров (Chat Completion) | **Опции** | сэмплеры → **отдельный** вход `API` |
| Сэмплеры Text Completion + порядок (koboldcpp/ooba) | **Локал-сэмплеры** | «умные» крутилки → тот же вход «Опции» `API` |
| Провайдер + ключ + модель + сам вызов | **API** | ответ модели → в `Чат` |
| Окно чата (ввод + история сообщений) | **Чат** | ввод пользователя; история → в комплитер; приветствие засевается авто от подключённого `Персонажа` (ножку «Первое сообщение» убрали). Внизу **две сервис-ножки**: **«Последнее сообщение»** (`in:lastmes`) — текст подключённой ноды в самый конец промта; **«Хроника»** (`out:chronicle`) — сцены чата → нода `Хроника`. Кнопка **🕯** — читалка памяти этого чата + смысловой поиск (тест активации: память + лорбук по смыслу и ключам). Значок-список — **«Оглавление»** (главы Хроники, прыжок к сцене), открывается внутри чата |
| Тема Moonlit / живой рендер сообщений | **Чат** (iframe ST+Moonlit) + **«око»** | настоящий чат прямо в ноде; «око» разворачивает ту же ноду на весь экран |
| *(RLM-слой, идея SW soul-md)* | **Душа** | память MD+RAG → плашка «Память» (движок читает+пишет); список доков, у каждого свой вход-коннектор для инструкции, а под доком — что ИИ уже записал |
| *(RLM-слой, референс MemoryBooks/MachineMechanic)* | **Хроника** | сцена диалога → модель сжимает в запись `{заголовок, текст, ключи}` → в **«Лорбук чата»** (архив по ключам, нумерованные главы). Вход ← сервис-порт «Хроника» ноды `Чат`; выход → нода `Лорбук чата`. Авто-сводка раз в N сообщений + ручная кнопка. **Не `Душа`** (та — динамичная MD-память), а структурный архив сцен |
| *(RLM-фишка, в ST нет)* | **Режиссёр** | события → плашка «События» (`In-chat @1`) |
| *(RLM-слой, эмуляция сэмплера DRY на облаке)* | **Программный DRY** | англ-блок «не повторяй эти фразы» (авто-повторы из истории + 2 ручных банка + свежесть) → **веерный выход**: плашка комплитера (`In-chat @0`) И/ИЛИ разъём «Анти-повтор» ноды `Критик` |
| Objective (плагин `SillyTavern-Objective` / `MachineMechanic`) | **Цель** | цель → список задач; текущая (первая невыполненная) задача — **веерный выход**: плашка «Цель» комплитера (`In-chat @0`, рядом с «Состоянием») И/ИЛИ разъём «Цель» ноды `Критик` (опц., тумблеры Контекст/Мотиватор в самой «Цели»). Фоном проверяет выполнение раз в N ответов; «🎲 Придумать цель» — ИИ сам формулирует цель из рыхлого намёка/сцены. Вход ← сервис-ножка «Цель» ноды `Чат` |
| *(движок эмбеддингов)* | **Эмбеддер** | боковой сервис → `Лорбук` (semantic) / `Душа` (RAG) |
| *(отладка, как консоль ST)* | **Консоль** | журнал запросов к модели: промт/параметры/ответ. Самостоятельная — без проводов. Терминальный вид |
| *(честный предпросмотр сборки)* | **Сканер** | вход ← выход ноды; по каждой плашке: имя + реальный контент (та же `plateContent`, что в запрос). Терминальный вид |

## Правила визуализации (с ними сверяемся)

1. **Провод = поток данных в одну сторону** (выход справа → вход слева). Это **не** сигнал запуска. Запуск генерации — **кнопка «отправить»** в `Чате`, а не провод.
2. **Каждый провод несёт конкретный кусок** (имя, лорбук, промт, сэмплеры), а не «весь запрос целиком».
3. **`Опции` — боковой вход в `API`**, а не звено «в разрыв» линии. Нет ноды/провода Опций → идут **дефолтные** настройки. (Так же можно отключать любой источник — просто не подключать его.)
4. **Направление данных:** Персонаж/Лорбук → Комплитер → API → Чат; Опции → API. **Никакого «кольца» назад в API** — данные не ходят по кругу; ощущение кольца оттого, что в `Чат` и пишут, и читают ответ.
5. **История чата** — не отдельный источник-провод, а **плашка**, которая сама берёт содержимое из подключённого `Чата`. Появляется, когда комплитер дотягивается до чата — напрямую **или через `API`** (`комплитер → API → Чат`).
6. У `API` слева **два подписанных входа**: «Промт» и «Опции». Справа — один выход (ответ).
7. **Лорбук персонажа** — встроенный в карточку лорбук при загрузке **материализуется** в отдельную ноду `Лорбук` (провод `Персонаж.Лорбук → Лорбук`); данные копируются в ноду и живут в ней. К комплитеру этот `Лорбук` подключается вручную.
8. **`Опции` vs `Локал-сэмплеры`** — обе кормят один вход «Опции» `API`, но это **разные семейства ST**: `Опции` = Chat Completion (то, что реально глотает облачный OpenAI-совместимый API); `Локал-сэмплеры` = Text Completion своих движков (DynaTemp, Min P, Smoothing, Mirostat, DRY, XTC) — по облачному API **не уходят**, живут только на локальном бэкенде. Порядок сэмплеров (`sampler_order`) **двигается** только у той группы, где позиция реально меняет результат (верхняя секция ноды); «умные» крутилки применяются в фиксированных точках и не переставляются.
9. **Режим ноды `API` = тип подключения ST** (Chat Completion ↔ Text Completion). Это тот же выбор, что в панели подключения ST. От него зависит, какое семейство сэмплеров осмысленно: Chat → `Опции` (облако: OpenRouter и прямые провайдеры); Text → `Локал-сэмплеры` (свой движок koboldcpp/ooba **или** RP-хостинги ArliAI/Infermatic/Featherless/Mancer на Aphrodite). Пресеты RP-хостингов ставят режим Text сами. **Один и тот же режим Text** покрывает и «облачные умные крутилки» (хостинги), и локальный движок — отдельной ноды под локалку не нужно, нужна вторая «дверь» у `API`.
10. **Три scope лорбука — одна нода.** `Лорбук` бывает трёх областей — мир / персонаж / чат — и каждая льётся в **свою** плашку комплитера («World Info» / «Лорбук персонажа» / «Лорбук чата»). **Область выбирается дропдауном и видна в имени ноды** («Лорбук · World Info» и т.п.) — нода одна, в пресете три экземпляра. Сама нода — мини-приложение (слева список записей, справа редактор записи), **глазок** в шапке → на весь экран. *(В ST World Info — это движок, читающий все лорбуки; у нас scope разнесён на явные плашки — см. `backend-research.md` §8.)*
11. **`Эмбеддер` — боковой сервис** (как `Опции`): выход → боковой вход `Лорбук` (для `semantic`/`vectorized`-записей) и `Душа` (RAG). **Бэкенд настоящий** (родной ONNX ST, многоязычная модель): при подключении semantic-записи и RAG памяти реально считаются; не подключён → смысловой поиск выкл, лорбук по ключам. К `Режиссёру` **не** идёт — его триггеры (`range`/`random`/`chain`) не смысловые.
12. **`Режиссёр` → плашка «События»** (вставка `In-chat @глубина`, рядом с ответом — теперь **реальная**, см. п.13). **`Душа` → плашка «Память»**: нода = **список доков памяти** (Дневник / Статус / Мир / Психика / Темы), у **каждого дока свой левый вход-коннектор** — по аналогии с плашками комплитера. Что и как писать в конкретный док задаёт **обычная нода `Систем промт`**, подключённая в этот коннектор (свою ноду под промты **не плодим** — `Систем промт` универсальна). Дефолтные доки только выключаются, свои — удаляются; **под каждым доком видно, что ИИ уже написал**. **Движок памяти рабочий (обе стороны):** читает (RAG-память → плашка «Память») и пишет (ИИ ведёт доки раз в `batch` реплик + кнопка «Обновить память сейчас») — нужен подключённый `API`/`Эмбеддер`. Оба слоя **опциональны**: пусто/не подключено → ведёт себя как ST. `Режиссёр` — уже рабочий (движок событий `range`/`random`/`chain`).
13. **Позиция плашки комплитера — две категории.** `Relative` — плашка стоит в общей последовательности (место = порядок сверху вниз). `In-chat` — плашка **вне последовательности**, вставляется в собранный промт на **глубину N** от конца (N=0 — в самый конец, N=1 — перед последним…); при равной глубине несколько плашек идут в порядке, как они **стоят** (перетаскивание, сверху = раньше) — без числового поля. В UI комплитера In-chat-плашки **визуально отделены** в отдельную зону, сгруппированы по глубине. **Канон ST** (сверено с `PromptManager.js`: `chatCompletionDefaultPrompts`/`promptManagerDefaultPromptOrder`): в дефолте **все** промпты `Relative`; in-chat по глубине — ручная опция на конкретный промпт (`injection_position: ABSOLUTE`), а не дефолт. Порядок ST: `main → World Info(before) → Persona → Char Desc → Char Personality → Scenario → Enhance(off) → Auxiliary → World Info(after) → Chat Examples → Chat History → Post-History`. **В пресете RLM In-chat стоит только у «События»** (@1) — аналога дефолтного промпта в ST нет, а близкий по смыслу **Author's Note** в ST именно in-chat по глубине.
14. **Нода `Систем промт` — источник плашки `Основной промт` (main).** Держит твою инструкцию; в левый вход по проводу приходит **системный промт персонажа** (поле `system_prompt` карточки, у ноды `Персонаж` под него есть выход «Систем-промт»). Селект **«Смешивание»** — **Только свой / Только входящий / Совместить** (у «Совместить» — порядок «сначала свой» / «сначала входящий») — решает, что уйдёт на выход. «Входящий» — это то, что пришло по проводу (промт персонажа из карточки, `Душа` или любой источник — не только персонаж). Это **RLM-слой сверх ST**: в чистом ST `system_prompt` карточки просто **перебивает** main (override, без совмещения). Поэтому у плашки `main` в комплитере **нет** чекбокса «Запретить перебивание карточкой» — весь спор «свой vs персонажа» живёт в режимах этой ноды. Чекбокс остаётся только у «Инструкций после истории» (`jailbreak`), где аналогичной ноды пока нет. Провод персонажа не подключён → на выходе только свой текст (правило №3).

## Поток при генерации (коротко)

1. Пишешь сообщение в `Чат` → это запускает цепочку.
2. **Async-подготовка** (до сборки): RAG-память (`Душа` → плашка «Память») + близость сцены к semantic/vectorized-записям лорбука (кэш для срабатывания).
3. `Промт комплитер` собирает `messages`: плашки по порядку ST, контент — из подключённых источников (Персонаж, Лорбук, История чата, системные промты, Память). Лорбук отдаёт записи **по приоритету `order` в пределах токенного бюджета** («% от контекста»); лишнее срезается.
4. `API` склеивает `messages` + сэмплеры из `Опций` → одно тело запроса.
5. Звонок провайдеру (через сервер) → ответ модели → в `Чат`.
6. **После ответа:** раз в `batch` реплик движок памяти обновляет доки `Души` на диске (фоном).

## Чего НЕ делаем

- Не изобретаем поведение, которого нет в ST.
- Не кладём сэмплеры в текст промта.
- Не делаем провода «управляющими» (control-flow) — только данные.
