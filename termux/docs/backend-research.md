## 1. Развенчание исходных предположений

Перед исследованием было два ошибочных допущения. Оба неверны:

- **«SW написан на Vue»** — нет. SW это **Python + PyQt6** десктоп. Vue там нет вообще. Его «браузерность» — это встроенный в Qt Chromium (`PyQt6-WebEngine`) для рендера Live2D/VRM-аватаров, а не веб-архитектура.
- **«ST работает с файловой системой по-своему через JS»** — важное уточнение о том, как это вообще устроено (см. ниже), потому что это ядро твоего вопроса.

### Как браузерное приложение работает с файлами (ключевой момент)

Браузерный JavaScript **не имеет прямого доступа к файловой системе** — это запрещено политикой безопасности браузера. Поэтому «чисто браузерного» решения, которое само пишет файлы на диск, не бывает. У ST архитектура **клиент-сервер**:

```
[ Браузер (телефон/ПК) ]  ← HTTP/REST →  [ Node.js-сервер (Termux) ]  ← files →  [ Диск ]
     public/*.js                            src/endpoints/*.js               data/…
   рисует UI, строит промпт            читает/пишет PNG, JSONL, JSON
```

- **Сервер** (Node.js) — единственный, кто трогает диск. Он отдаёт REST-эндпоинты `/api/characters`, `/api/chats`, `/api/worldinfo` и т.д.
- **Фронтенд** (JS в браузере) — только рисует интерфейс и ходит на эти эндпоинты по HTTP.

Именно эта модель даёт то, что тебе нужно: **сервер крутится в Termux на Android, а UI открывается в браузере** (хоть на том же телефоне через `localhost`, хоть с другого устройства по IP). SW так не умеет: его «веб-клиент» — это тонкий пульт, который по WebSocket дёргает **живой Qt-объект на десктопе** (`interface_signals.py`, 725 КБ логики). Без запущенного Qt-приложения сервер SW мёртв.

**Вывод:** для цели «сервер в Termux + браузер» подходит только модель ST. Это не вопрос вкуса — это единственный жизнеспособный путь.

## 2. Почему ST портируется в Termux, а SW — нет

Причина техническая и решающая — **нативные зависимости** (модули, требующие компиляции под конкретный процессор/ОС).

### ST: осознанный отказ от нативного кода

Проверка `node_modules` на `.node`-бинарники → **0 файлов**. Всё, что обычно требует нативной сборки, заменено на pure-JS или WASM:

| Задача | Обычное (нативное) решение | Что использует ST |
|---|---|---|
| Обработка картинок | `sharp`, `canvas` (node-gyp) | **Jimp** + WASM-кодеки (`@jimp/wasm-png/jpeg/webp/avif`) |
| Токенизация | нативные биндинги | `tiktoken` (WASM), `sillytavern-transformers` (ONNX/WASM) |
| БД | `better-sqlite3`, `sqlite3` | **файлы** (`node-persist`, `write-file-atomic`) |
| Векторы/RAG | нативная векторная БД | `vectra` (чистый JS, файловый индекс) |
| Git | нативный libgit2 | `simple-git` (обёртка над CLI) |

В коде даже есть спец-ветки под Android: `const isAndroid = process.platform === 'android'` (отключает кэш карточек ради экономии ОЗУ; не поднимает браузер автоматически). `npm install` под Termux проходит без единой нативной сборки — вот почему ST там официально работает.

### SW: фундаментальные блокеры

- `torch==2.10.0+cu128` / `torchaudio` / `torchvision` — сборки под **CUDA x86-64**, на Android неприменимы.
- `PyQt6` + `PyQt6-WebEngine` — под Termux нет готовых wheels, QtWebEngine на Android практически не собирается.
- Вшитый `llama-server.exe` + `ggml-*.dll` — **Windows PE-бинарники**.
- `pywin32`, `win32_setctime`, `ctypes.windll` — **только Windows**.
- Десятки тяжёлых нативных пакетов: `coqui-tts`, `rvc-python`+`fairseq`, `faster-whisper`, `vosk`, `faiss-cpu`, `spacy`, `numba`/`llvmlite`, `PyAudio`, `live2d-py`, `PyOpenGL`, `playwright`.

Портировать SW на Android = переписать заново. Легко переносимы только его **Qt-независимые модули**: LLM-провайдеры (`providers/*.py`), конструктор промптов (`prompt_engine.py`), формат хранения (`configuration.py`), память (`soul_memory.py`).

## 3. Форматы данных — сердце вопроса (MD vs PNG+JSON vs JSONL)

Здесь главный интерес. Разберём, что и почему используют оба проекта, и выведем модель для RLM.

### Что используют референсы

**ST — персонажи = PNG со встроенным JSON:**
- Один `.png` = аватар + все данные. JSON лежит в `tEXt`-чанке PNG, закодированный в base64. Ключ `ccv3` (Character Card v3) приоритетно, иначе `chara` (v2).
- Библиотеки: `png-chunks-extract`, `png-chunk-text`, запись через собственный `src/png/encode.js` (пересчёт CRC).
- Физически: `data/default-user/characters/*.png`.
- Поля v2: `name, description, personality, scenario, first_mes, mes_example, system_prompt, post_history_instructions, alternate_greetings[], character_book, tags, creator, extensions{...}`.

**ST — чаты = JSONL (одна строка = одно сообщение):**
- `data/default-user/chats/<Персонаж>/<чат>.jsonl`.
- Строка 1 — метаданные (`user_name, character_name, create_date, chat_metadata{...}`).
- Строки 2..N — сообщения: `{name, is_user, is_system, send_date, mes, extra{...}, swipes[]}`.
- Запись: `chatData.map(JSON.stringify).join('\n')` атомарно. Чтение построчно.

**ST — миры/лорбуки = JSON:**
- `data/default-user/worlds/*.json`, структура `{entries: {0:{...}, 1:{...}}}`.
- Запись: `key[]` (regex-триггеры), `content`, `constant`, `order`, `position`, `depth`, `probability`, рекурсия, timed-эффекты (`sticky`/`cooldown`/`delay`).

**SW — память = Markdown (!):**
- Долговременная «Soul Memory» хранится в `.soul/<Персонаж>/chats/<id>/memory/`: `MEMORY.md`, `USER.md`, `topics/*.md`.
- Отбор релевантных заметок — семантический RAG по эмбеддингам `all-MiniLM-L6-v2`.
- Инжектится в промпт блоком `[CHARACTER PSYCHOLOGY & COGNITIVE CACHE]`.
- **Важный сигнал:** один из референсов уже использует MD — но именно для **медленного, авторского, накапливаемого** контента (память/знания), а не для горячего лога чата.

### Почему ST по умолчанию НЕ использует Markdown

Не потому что MD плох, а потому что для его задач проигрывает по трём осям:

1. **Переносимость** — карточка v2/v3 в PNG путешествует одним файлом-картинкой (аватар + данные вместе). Кинул картинку на Chub/форум/в чат — там уже всё. MD даёт текст + отдельную картинку.
2. **Экосистемная совместимость** — Card v2/v3 это де-факто стандарт всей ниши (ST, RisuAI, Agnai, Chub, Backyard). MD-стандарта карточек **не существует**. Отказ от PNG+JSON = отрезать себя от тысяч готовых карточек.
3. **Структурность** — жёсткая схема полей + валидация (`TavernCardValidator`). Промпт-конструктор берёт поля по именам. В MD поля пришлось бы парсить эвристикой по заголовкам — хрупко. Лорбук (`character_book`) — это дерево, а MD плоский.

В ST Markdown используется **только как формат рендера сообщений в UI** (`showdown` + `dompurify`), не как хранилище.

### Честная таблица: MD vs PNG+JSON vs JSONL

| Критерий | Markdown (+YAML frontmatter) | PNG + встроенный JSON | JSON / JSONL |
|---|---|---|---|
| Человекочитаемость | ★★★ отлично | ✗ base64 в бинаре | ★★ сносно |
| Ручное редактирование | ★★★ любой редактор | ✗ только спец-тул | ★★ можно, но легко сломать |
| Git-диффы / merge | ★★★ идеально | ✗ бинарь, диффа нет | ★★ построчно ок (JSONL) |
| Grep / поиск по файлам | ★★★ | ✗ | ★ |
| Один файл = аватар+данные | ✗ (текст + картинка отдельно) | ★★★ | ✗ |
| Совместимость с индустрией | ✗ нет стандарта | ★★★ Card v2/v3 | ★★ (JSONL-чаты ~совместимы) |
| Структурность / валидация полей | ★ (нужны конвенции) | ★★★ | ★★★ |
| Вложенные структуры (лорбук) | ✗ плоский | ★★★ | ★★★ |
| Append (дописать сообщение) | ✗ | — | ★★★ (JSONL) |
| Устойчивость к битым данным | ★★ | ✗ (ресайз убивает чанки) | ★★★ (битая строка не рушит файл) |
| Метаданные на сообщение (свайпы, токены) | ✗ неудобно | — | ★★★ |

**Вывод из таблицы:** нет одного победителя. У каждого формата своя зона силы:
- **MD** силён на медленном, авторском, прозаичном, редактируемом-руками контенте.
- **PNG+JSON** незаменим только для одной задачи — **обмен карточками с экосистемой**.
- **JSONL** оптимален для быстрого append-only лога с метаданными на сообщение.

## 4. Рекомендуемая модель хранения для RLM

Идея RLM «отличается в корне» — и корректная реализация этого отличия не «MD вместо всего», а **правильное разделение по типу контента**. Именно так (неявно) сделал и SW: config/JSON для горячего состояния чата, MD — для медленной памяти.

### Принцип: три слоя по скорости изменения

```
МЕДЛЕННЫЙ, авторский, читаемый    →  Markdown + YAML frontmatter   ← идентичность RLM
(персонажи, персоны, лорбуки,        (git-friendly, редактируется
 миры, память, саммари)               в любом редакторе)

БЫСТРЫЙ, append-only, машинный     →  JSONL
(лог чата: сообщения, свайпы,         (быстрый дозапись, крашеустойчив,
 токены, timestamps, reasoning)        метаданные на сообщение)

ОБМЕН с внешним миром             →  PNG (Card v2/v3) + ST-JSON
(импорт/экспорт карточек и миров)     (адаптеры, не основное хранилище)
```

### Предлагаемая структура на диске

```
data/<user>/
  characters/
    ayaka-shindo/
      character.md          # YAML frontmatter (name, tags, creator, voice…) + MD-тело
      avatar.png            # обычная картинка, БЕЗ встроенных данных
      lore/
        capital.md          # запись лорбука: frontmatter (keys, order…) + MD-контент
        magic-system.md
      memory/
        MEMORY.md           # идея из SW: накапливаемая долговременная память
        summary.md          # авто-саммари старой истории
  chats/
    ayaka-shindo/
      2026-07-30_evening.jsonl   # горячий лог (как у ST)
  personas/
    leon.md
  worlds/
    eldoria.md              # мир целиком как MD-документ
```

Пример `character.md`:

```markdown
---
name: Ayaka Shindo
tags: [tsundere, student]
creator: leon
version: 2
voice: { engine: edge-tts, id: ja-JP-NanamiNeural }
lorebook: [capital, magic-system]
---

## Description
Ученица-отличница, скрывающая…

## Personality
Гордая, вспыльчивая, но заботливая под маской.

## Scenario
{{user}} впервые встречает {{char}} в библиотеке академии.

## First message
*Айака поднимает взгляд от книги…*

## Example dialogue
{{user}}: Привет.
{{char}}: Ч-что тебе нужно?..
```

**Ключевой приём — адаптеры, а не жёсткий формат.** Каноническое хранилище MD-first, но **импорт/экспорт в PNG Card v2/v3 и ST-JSON — обязателен**. Это даёт лучшее из всех миров:
- Автор редактирует MD в любом редакторе, версионирует в git.
- «Поделиться» / «залить на Chub» → кнопка экспорта собирает PNG v3 на лету.
- «Импортировать с Chub» → адаптер разбирает PNG, раскладывает в MD-папку.
- Совместимость с тысячами готовых карточек сохраняется.

**Про чаты честно:** не стоит хранить горячий лог чата в MD. Свайпы, токены, reasoning, метаданные на сообщение и быстрый append — это ровно то, где JSONL выигрывает, а MD-парсер стал бы хрупким (markdown-контент сам содержит `##`, ломая разделители). Решение: **JSONL как рантайм-хранилище + экспорт чата в MD** как читаемый транскрипт/архив. Так MD-любовь удовлетворяется там, где она уместна, без жертв на горячем пути.

## 5. Выбор основы бэкенда

Модель — однозначно ST-подобная (Node.js-сервер + браузерный фронт + файловое хранилище + pure-JS/WASM зависимости). Остаётся вопрос: **форкать ST или писать своё**.

### Вариант A — форкнуть SillyTavern

- **Плюсы:** мгновенно фичакомплит; тысячи карточек, лорбуки, все LLM-провайдеры, Termux из коробки.
- **Минусы:** фронт — монолит `public/script.js` на **10 000+ строк jQuery**; гнуть его под «MD-first в корне» — борьба с чужим кодом. Лицензия **AGPL-3.0**: любой производный продукт, отдающий UI по сети, обязан открыть исходники под AGPL.

### Вариант B — greenfield Node-сервер, ST-совместимый по форматам ⭐ рекомендуемый

- Свой чистый сервер (Express / Fastify / Hono) + современный фронт, но **переиспользовать проверенные библиотеки ST**, а не изобретать:
  - `png-chunk-text` + `png-chunks-extract` (MIT) — карточки v2/v3
  - `Jimp` + WASM-кодеки (MIT) — картинки без нативной сборки
  - `tiktoken` (WASM) — подсчёт токенов
  - `vectra` (чистый JS) — RAG/векторы для памяти
  - `handlebars` / `yaml` — шаблоны промптов и frontmatter
- Быть **import/export-совместимым** с Card v2/v3 + JSONL — сохраняем доступ к экосистеме.
- Свободно выбрать лицензию (все перечисленные либы — MIT).
- Даёт чистую MD-first архитектуру, которую хотелось «в корне».

**Рекомендация: Вариант B.** Идея RLM отличается в корне (MD-first native + адаптеры), а под такое чужой 10k-строчный монолит гнуть дороже, чем собрать чистое ядро на тех же проверенных кирпичах. Стек: **Node 18+ (Termux-совместим), Fastify или Express, файловое хранилище, все зависимости pure-JS/WASM.**

### Что своровать у каждого референса

| Из ST берём | Из SW берём |
|---|---|
| Клиент-серверную модель (сервер = FS, браузер = UI) | Идею **MD-памяти** с RAG (`MEMORY.md` + эмбеддинги) |
| Формат Card v2/v3 (как адаптер импорт/экспорт) | Блочный конструктор промпта с настраиваемым `order` |
| JSONL для лога чата (+ свайпы, метаданные) | Мульти-провайдерную фабрику LLM (OpenAI-совместимый слой) |
| Модель World Info (regex-триггеры, позиции, рекурсия) | Идею RPG-переменных состояния (`<state_update>`) |
| Pure-JS/WASM набор зависимостей (Termux) | `CUSTOM_ENDPOINT_URL` → внешний Ollama/koboldcpp |

## 6. Инструкт-теги / шаблоны под модель — как решают референсы (доп. исследование, 2026-08-08)

Проблема: в Text Completion промт — одна raw-строка, обёрнутая тегами инструкт-шаблона модели (ChatML `<|im_start|>`, Llama-3 `<|start_header_id|>`, Mistral `[INST]`…). Разным моделям — разные теги.

**SillyTavern — своя библиотека + деривация:**
- **37 встроенных инструкт-шаблонов** (`server/default/content/presets/instruct/*.json`): ChatML, Llama 2/3/4, Mistral V1–V7, Alpaca, Vicuna, Gemma, Command R, DeepSeek, Metharme и др. Поля: `input_sequence`/`output_sequence`/`system_sequence` (+суффиксы, first/last), `stop_sequence`, `wrap`, `names_behavior`, `activation_regex`, `bind_to_context`.
- Применяется **только в Text Completion** (`main_api !== 'openai'`); в Chat Completion инструкт выключен — теги ставит провайдер.
- Выбор шаблона под модель: (1) ручная привязка «Bind to model»; (2) `activation_regex` по имени модели — **но у встроенных пустой**, из коробки не срабатывает; (3) `bind_to_context` (инструкт+контекст синхронно); (4) **деривация из `chat_template` модели** (koboldcpp/llama.cpp отдают шаблон+хэш → ST узнаёт по таблице хэшей или характерным тегам).
- Сборка строки — `formatInstructModeChat/StoryString/Prompt` в `server/public/scripts/instruct-mode.js`.

**Soul of Waifu — не клеит теги вообще:**
- Всегда `messages` (роли) → **chat-эндпоинт**, и облако, и локальный `llama-server`. Своей библиотеки шаблонов нет.
- Локаль: messages на `/v1/chat/completions` llama.cpp → **llama.cpp применяет GGUF-шаблон** (jinja `chat_template` из метаданных). По умолчанию **Auto**.
- Override — дропдаун **Auto/ChatML/Llama-3/DeepSeek/Qwen/Mistral/Alpaca** → флаг `--chat-template`. Автоподбора по имени модели нет.
- «Теги», что SW пишет сам, — семантические маркеры *внутри* content (`[CHARACTER PROFILE]`, `<state_update>`), не разделители инструкта.
- Файлы: `app/utils/ai_clients/prompt_engine.py`, `.../providers/local_provider.py`, `.../local_server_manager.py`.

**Вывод для RLM:** идём путём SW — `messages` → chat-эндпоинт, теги на модели/провайдере. koboldcpp тоже даёт chat-эндпоинт с GGUF-шаблоном → локаль можно вести через chat-дверь без ручных тегов. Своя raw-сборка нужна только ради `sampler_order` (отложено); понадобится — хватит SW-стиля override (Auto/ChatML/Llama/Mistral), а не 37-шаблонной машинерии ST.

## 8. Как устроен World Info в ST: движок vs источники (доп. исследование, 2026-08-08)

**Главное:** «World Info» в ST — это **движок** (машина, что читает лорбуки, матчит по ключам и вставляет в промпт), **а не сам лорбук**. Лорбуки — это **файлы-источники** для него.

**Пруф по коду `public/scripts/world-info.js`:** функция `getSortedEntries()` (строка 4306) собирает записи из **четырёх источников** через `Promise.all` и сливает в один массив:

| Источник (функция) | Что грузит | Где хранится файл |
|---|---|---|
| `getGlobalLore()` (4243) | глобальные лорбуки | отдельные `worlds/*.json`, цепляешь в панели |
| `getCharacterLore()` (4191) | лорбук персонажа | **внутри карточки** (`character.data.extensions.world`) |
| `getChatLore()` (4260) | лорбук чата | привязан к чату (`chat_metadata[METADATA_KEY]`) |
| `getPersonaLore()` (4280) | лорбук персоны | привязан к персоне |

Каждая функция-источник **только грузит** файл (`loadWorldInfo(name)` → сырые записи) и отдаёт движку. Обработки в источниках нет.

**Почему лорбуки не работают без World Info:** лорбук = `.json` `{entries:{…}}` — мёртвые данные. Единственный код, что их читает / активирует по ключам / вставляет — движок WI (`getSortedEntries` → активация → инъекция). Без него `character_book` — просто JSON, который никто не открывает.

**Почему «лорбук персонажа» — отдельная сущность, хотя движок один:** разница не в движке, а в **месте хранения** (в карточке / отдельный файл / в чате). Один движок читает все три. Аналогия: **World Info = принтер, лорбуки = лотки бумаги** — разные лотки, один принтер; без принтера бумага бесполезна.

**Пруф, что конвейер один:** `getCharacterLore` **пропускает** книгу, если она уже активна как global/chat/persona (строки 4215-4228) — дедуп между источниками возможен только внутри **одного** пайплайна.

**Для RLM:** мы разносим лорбуки на **три явные плашки-входа** по scope (`World Info` / `Лорбук персонажа` / `Лорбук чата`) — в ST это один слитый конвейер с позицией на каждую запись, у нас — три отдельных входа. Чётче для нодового UI (реализовано в базовом пресете; см. `plan-lorebook-vector.md`, `app-guide.md`).
