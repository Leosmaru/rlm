# RLM — Журнал решений (что и почему)

> **Устав документа**
> - **Зачем:** хранить принятые решения и их обоснование, чтобы не пере-решать по кругу.
> - **Что сюда пишем:** одно решение — один блок: что решили, почему, альтернативы.
> - **Чего НЕ пишем:** пошаговые логи правок (это `changelog.md`), описание текущего кода (это `architecture.md`).
> - **Правило ведения:** добавляем блок при новом решении; старые не переписываем, а при отмене помечаем «пересмотрено».

## Р-1. Бэкенд = SillyTavern + свои плагины (не greenfield, не форк — пока)
Модель ST (Node-сервер + браузер + файлы + pure-JS/WASM) — единственная под цель «сервер в Termux + браузер». У пользователя уже есть рабочий плагин `soul-md`. Форк vs greenfield отложено, сейчас строим поверх ST. Подробно — `backend-research.md`.

> **Пересмотрено Р-9 (2026-08-07):** «форк vs greenfield отложено» снято — пользователь выбрал шейп «RLM = своё приложение на моторе ST».

## Р-2. Форматы: карточки и лорбуки — JSON, память — MD
Карточки/лорбуки в JSON — родной формат ST и совместимость с экосистемой (нравится пользователю). MD — для памяти (читаемо, как в Soul of Waifu). Горячий лог чата — JSONL (append + метаданные), не MD.

## Р-3. Лицензия ST (AGPL-3.0) — приемлема
Для личного использования не обязывает ни к чему. При раздаче другим — исходники остаются открытыми; закрыть/сделать проприетарным нельзя. Это совпадает с целью пользователя: «раздавать бесплатно, но защитить от присвоения». Детали — память `rlm-license-agpl-note`.

## Р-4. Дуальный режим на одном бэкенде
Тяжёлый режим на ПК (локальные модели, TTS, аватар) / лёгкий в браузере на телефоне. Один сервер, общие данные. Мобильное ограничение касается только того, что крутится внутри телефона; на ПК тяжёлые движки подключаются снаружи.

## Р-5. Electron — опциональная ПК-обёртка
На ПК заворачиваем веб-приложение в Electron-окно ради десктоп-ощущения (у ST есть `start:electron`). Бэкенд не меняется. На телефоне Electron не используется.

## Р-6. Система документации
Каждый документ с уставом; INDEX — только карта; история только в changelog; состояние правится где менялось; новый документ — по подтверждению. Правила — память `rlm-docs-rules`.

## Р-7. Чат-погружение = настоящий ST+Moonlit (копия CSS в изолированном iframe)
Не имитировать вид вручную (тупик — бесконечная подгонка) и не подключать живой сервер ST (пользователь этого не хотел). Вместо этого — **скопировать реальные CSS** ST-ядра + Moonlit в `app/moonlit/`, воспроизвести DOM-структуру чата ST в `chat.html`, подставить переменные темы пользователя (Cappuccino, вытащены из живого ST). Панель опций — **генерируется из копии конфига плагина** (`moonlit-settings.js`), а не пишется руками. Итог: вид и опции настоящие и самодостаточные (без запущенного ST). Изоляция — `iframe` (чтобы CSS ST не ломал узловой UI). Обмен — `postMessage`.

## Р-8. Фронтенд = узловое рабочее пространство (Electron-прототип)
UI RLM — **холст с нодами** (визуализация потока: `API`/`Опции`/`Систем промт`/`Чат` соединяются проводами), а не классический список чатов как в ST. Прототип — ванильный JS в Electron. «Нырок» из ноды чата открывает полноэкранный ST+Moonlit-чат (см. Р-7).

## Р-9. RLM — своё приложение на моторе SillyTavern (весь код наш)
Уточняет Р-1. RLM — **не** надстройка/плагин внутри ST и **не** greenfield-переписывание, а **самостоятельное приложение**, у которого SillyTavern работает **движком внутри**. Снаружи это RLM (свой узловой интерфейс, своё имя, свой запуск), ST не виден. Практически: делаем свою копию мотора ST в проекте и владеем всем кодом, правим напрямую.
Почему: пользователю важна идентичность «это моё приложение, а не добавка к чужому» — слово «плагин» применительно к RLM в целом он отверг. При этом греть готовый мотор ST (сервер, форматы, Termux, встроенные движки) выгоднее, чем писать с нуля.
Альтернативы: (а) **надстройка внутри ST** — отверг пользователь; (б) **greenfield с нуля** — выбрасывает готовый мотор ST. Выбран третий вариант — «своё приложение на моторе ST».

## Р-10. Топология рантайма: промт и сэмплеры отдельны, склейка — в ноде `API`
Промт (`messages`, «ЧТО читает модель») и сэмплеры (нода `Опции`, «КАК выбирает слово») — **разные потоки**, в тексте промта не смешиваются. В запросе к провайдеру они лежат рядом (`{ messages, temperature, … }`), и объединяются **только в момент звонка** (нода `API` = звонок; технически — серверный маршрут `rlm.js`). Поэтому у `API` **два входа**: «Промт» и **«Опции» боковым входом** (не «в разрыв» линии).
Почему: сэмплеры — математика на выходе модели, а не текст; «вписать» их в промт нельзя. Отдельный вход сохраняет развязку (тот же промт крутить разной температурой) и не обманывает направление данных (данные не ходят «кольцом» назад в `API`).
Альтернативы: (а) `Опции` **инлайн-нодой** «в разрыв» `Чат → Опции → API` — отверг: нода ничего не преобразует, обман направления, «одна линия» лишь прячет второй провод выше; (б) `Опции` **в тексте промта** — противоречит формату запроса. Эталон визуализации — `node-logic.md`.

## Р-11. Умные сэмплеры — отдельная нода `Локал-сэмплеры` + режим Chat/Text у `API` (не вторая нода API)
Сэмплеры Text Completion (DynaTemp, Min P, Smoothing, Mirostat, DRY, XTC…) вынесены в **отдельную ноду** `Локал-сэмплеры`; у ноды `API` появился **переключатель Chat/Text** = тип подключения ST. Разделение: `Опции` = Chat Completion (облако), `Локал` = Text Completion (свой движок / RP-хостинги на Aphrodite). Гейт по режиму/сервису гасит недоступные крутилки (Chat → `Локал` серая целиком; Text → минус несовместимые сервисом, напр. Mancer без Mirostat).
Почему: облачный OpenAI Chat API умные крутилки не принимает — они живут только в Text Completion. Локальный движок — это тот же HTTP-звонок на другой Base URL, различие лишь в **типе подключения**, а не в отдельной ноде; поэтому режим — переключатель одной ноды `API` (как панель подключения в ST). Один вход «Опции» кормится `Опциями` **или** `Локалом` по режиму.
Альтернативы: (а) **вторая нода `API`** под локаль — отверг: адрес тот же, различие только в типе подключения → это режим; (б) умные крутилки **в общей `Опции`** — путает, т.к. в Chat не работают; (в) компромисс «базовые крутилки `Локал` активны и в Chat» — пробовали и **откатили**: в Chat `Локал` оказывается подмножеством `Опций`. Влияние **порядка** сэмплеров (`sampler_order`) — отложено (нужно только нативному koboldcpp).

## Р-12. Инструкт-теги — путь Soul of Waifu (chat-эндпоинт), не библиотека шаблонов ST
RLM собирает промт как `messages` и шлёт на **chat-эндпоинт**; теги/шаблон под конкретную модель ставит провайдер/движок сам (в т.ч. koboldcpp через свой chat-эндпоинт с GGUF-шаблоном). Свою библиотеку инструкт-шаблонов (как 37 у ST) — **не делаем**. Нативная raw-дверь koboldcpp (`/api/v1/generate` + ручная сборка строки по шаблону) — **отложена**, нужна лишь ради порядка сэмплеров.
Почему: изучены оба референса (`backend-research.md` разд. 6). SW теги не клеит вовсе (messages → chat-эндпоинт, шаблон применяет движок) — просто и надёжно. ST тянет 37 шаблонов + деривацию из `chat_template`, но **только для raw Text Completion**. Пока мы на chat-двери — теги не наша забота, «дефолт не подошёл модели» решает провайдер/GGUF.
Альтернативы: (а) **ST-way** (своя библиотека + деривация) — дорого и избыточно на chat-эндпоинте; (б) если raw-дверь понадобится — **минимальный override** как в SW (Auto/ChatML/Llama-3/Mistral), а не полная машинерия ST.

## Р-13. Три системы контента: `Лорбук` / `Душа` / `Режиссёр` (+ `Эмбеддер` как общий сервис)
SW сливает лорбук и режиссуру в один движок; RLM разводит на **три системы**, у каждой одна роль: **`Лорбук`** = знание о мире (3 scope: мир/персонаж/чат, приходит с карточкой), **`Душа`** = память (MD+RAG, только на чат, идея SW soul-md), **`Режиссёр`** = события сцены (`range`/`random`/`chain`, чисто RLM, автоматический). Смысловой поиск вынесен в **общий сервис — ноду `Эмбеддер`** (сменная модель, дефолт `multilingual-e5-small` под русский/Termux; можно несколько нод). Все три — **опциональные слои** поверх ST: не подключил → чистый ST.
Почему: у систем разная природа (статичное знание / быстрая MD-память / вброс событий), разное хранилище и темп — смешивать вредно; эмбеддер шарится потребителями, потому отдельная нода, а не настройка внутри лорбука. Лорбук разнесён по scope-плашкам — чётче слитного World Info-конвейера ST (в ST World Info — движок, читающий все лорбуки; см. `backend-research.md` §8). Схемы, движок матчинга и открытые вопросы — `plan-lorebook-vector.md`.
Альтернативы: (а) как SW — лорбук+режиссура в одном движке — отверг (путаница «режиссёр будто пишет память»); (б) память в чат-лорбук по ключам, как плагин MachineMechanic/MemoryBooks — у нас `Душа` = MD+RAG, другой путь; (в) векторизатор внутри `Лорбука` — отверг (общий сервис нельзя прятать в одного потребителя).

## Р-14. Систем-промт: совмещение своего и промта персонажа (RLM-слой сверх ST)
Нода `Систем промт` смешивает свою инструкцию и `system_prompt` карточки по режиму (**Только свой / Только персонажа / Совместить** + порядок). Чекбокс «Запретить перебивание карточкой» у плашки `main` — **убран**; спор «свой vs персонажа» целиком решают режимы ноды (единый центр).
Почему: в чистом ST `system_prompt` карточки просто **перебивает** main (override, без совмещения) — грубо; пользователю нужно управляемое совмещение (общая рамка + специфика персонажа). Дефолт «Совместить, сначала свой» безопасен: без провода персонажа = как раньше (только свой).
Альтернативы: (а) оставить ST-override + чекбокс — отверг (два места управления одним спором, нет совмещения); (б) дефолт «Только персонажа» (ST-канон) — не выбран, т.к. фича именно про совмещение.

## Р-15. Хранилище настроек/ключа — файл через главный процесс, не localStorage
Ключ и настройки `API` хранятся в **файле** `userData/rlm-store.json` (главный процесс, `fs.writeFileSync`, синхронный IPC `sendSync`); в браузере — фолбэк на `localStorage`. Обёртка `store` в `renderer.js`.
Почему: страница RLM грузится по `file://`, а её `localStorage` в Electron **ненадёжно переживает перезапуск** (opaque origin), плюс кнопка «Перезапуск» зовёт `app.exit(0)`, обрывая отложенную дозапись Chromium. `fs.writeFileSync` пишет на диск сразу и от этого не зависит. Симптом до фикса — «ключ опять пропал».
Альтернативы: (а) оставить localStorage — отверг (тот самый баг); (б) `app.quit()` вместо `exit(0)` — полумера, не покрывает `file://`-опасность. Граф/пресет пока на localStorage — переведём тем же `store`, если и они начнут теряться.

> **Пересмотрено Р-30 (2026-08-21):** появился свой сервер (Р-9), поэтому источник истины — он, а не файл/`localStorage`. Файловый `store` остался только под `rlm.tts.dtype` (PC-only).

## Р-16. Чат — живой ST+Moonlit прямо в ноде; «око» = разворот той же ноды (уточняет Р-7)
Настоящий ST+Moonlit (`iframe chat.html`) живёт **в самой ноде `Чат`**, а не только в отдельном полноэкранном погружении. В ноде он отрисован в «десктопной» логической ширине и вписан `transform: scale` — **точная мини-копия полного экрана** (при зуме холста разница не видна). «Око» разворачивает ту же ноду (анимация «нырка» сохранена), разворот синхронизирован с тем же диалогом. Диалог — динамический из `_msgs` (демо убрано, чат стартует пустым); ввод — в поле ST; работают «новый чат»/«перегенерировать»/правка; имена и аватары **долетают по проводам** от `Персонаж`/`Персона`.
Почему: раньше `chat.html` был статичным тест-диалогом в `#immersive`, не связанным с реальной генерацией — «нечестно». Пользователь хотел, чтобы нода честно рисовала интерфейс, а «око» просто фиксировало и приближало. Логическая ширина + scale даёт полноценную композицию ST в маленькой ноде без «обрезки».
Инструменты отладки (той же сессии): **`Консоль`** — журнал вызовов `rlmApi` (промт/параметры/ответ/finish_reason/токены, ключ скрыт); **`Сканер`** — честный предпросмотр сборки по плашкам через **ту же** `plateContent`, что идёт в запрос. Обе самостоятельные-«по требованию», терминальный вид, в пресет не входят.

## Р-17. Эмбеддер — родной ONNX ST на многоязычной модели; память для холста — маршруты `/api/rlm/soul` (до CSRF)
Векторы считает **родной** `getTransformersVector` ST (ONNX/WASM, без новых зависимостей). Модель — `Xenova/multilingual-e5-small` (в `config.yaml`), т.к. она **знает русский** (было `jina-en` — только англ.); e5 требует префиксы `query:`/`passage:`. Чтение/поиск памяти для узлового холста идёт через **новый `src/endpoints/rlm-soul.js`, смонтированный ДО CSRF** (как `/api/rlm`), а НЕ через плагин `soul-md` (он за CSRF — холст без токена до него не достучится). Данные — общая папка `plugins/soul-md/data`.
Альтернативы: внешний эмбеддер/облако — отклонено (локальность, Termux); ходить в плагин — нельзя из-за CSRF.

## Р-18. Дневник — семантический RAG «как в Soul of Waifu» (не «последние N», не целиком)
Выбор пользователя: `.md`-дневник в промт идёт **по смыслу** — эмбеддинг запроса vs записей, top-k + обрезка «хвостом», как в SW. Файл может расти сколько угодно — в контекст уходит горстка релевантного.
Альтернативы: «последние N по времени» (было в плагине) — теряет релевантность; «весь файл» — раздувает контекст (главное беспокойство пользователя).

## Р-19. Темы ≠ Лорбук — держим раздельно
Механика отбора у `Темы` (topic-док Души) совпадает с vectorized-лорбуком, но это **разные системы по сути**: лорбук — авторское знание (человек, едет в карточке, шарится), темы — рантайм-память ИИ (на чат, не шарится). В один UI не сливаем. Темы остаются доком `Души` (по умолчанию выключены — opt-in).

## Р-20. Термины «нода» vs «вижн»; интерфейс Души — удобный В НОДЕ
**Нода** — сам узел на холсте и его интерфейс; **вижн** — полноэкранный разворот ноды по «глазку» (`openLoreFs`). Правило: базовый интерфейс делаем удобным **в ноде**, вижн — бонус «крупно». Для `Души`: нода — одна колонка, секции «Доки памяти → Как ИИ ведёт память → …», а **записи, что ИИ уже написал, показываются ИНЛАЙН ПОД КАЖДЫМ ДОКОМ** (Дневник → его текст, Статус → его текст, …). Отдельное окно-оверлей записей было отвергнуто пользователем.

## Р-21. Менеджер персонажей и чатов (☰); «новый чат = дефолт»
> **Пересмотрено Р-23:** выпадающий ☰-менеджер заменён полноэкранным стартовым меню с системой пресетов.

Кнопка ☰ в тулбаре (перед «дискетой») → персонажи (регистрируются при загрузке карточки) → их чаты (имя + удалить) + «＋ чат». Концепт: каждая карточка живёт в общем **дефолт-пресете** (граф нод), который дособираем; выбор персонажа применяет карточку, выбор/создание чата — его состояние. **Новый чат = ДЕФОЛТ:** свежая память (`_chatId`), пустой чат, **лорбук персонажа ← `character_book` карточки**, **лорбук чата пустой**, **Душа пустая** (полноценного сохранения пока нет — старые записи прошлого персонажа не должны оставаться). Хранение пока в `localStorage`; серверный (дисковый) персистенс — позже.

## Р-22. Бюджет лорбука — по модели SillyTavern
Против «карточка сунула весь лорбук в промт»: сработавшие записи **сортируются по `order` (убыв.)** и заполняются до **токенного лимита = «% от контекста»** (дефолт 25% от «Опций», как ST `world_info_budget`); что не влезло — режется и помечается. Запись с **`ignoreBudget`** влезает всегда. Импорт `order`←`insertion_order`, `ignoreBudget`←`extensions.ignore_budget`. Токены — **оценка** (`len/3.5`), т.к. в браузере нет токенайзера (при нужде — серверный).
Альтернативы: только активация (как SW) — не спасает от кривых `always_on`-книг; без приоритета — режется случайное вместо важного.

## Р-23. Стартовое меню + система пресетов; контекстное сохранение
Развитие Р-21. При старте — полноэкранное **стартовое меню**: слева **пресеты** (пресет = сохранённая сборка графа; верхний = дефолт), справа **карточки персонажей** (аватар · дескрипшен · чаты). **Пресет ≠ чат:** новый чат рождается из дефолт-пресета, но дальше живёт своим снимком графа (`rlm.chatgraph.<id>`). **💾 контекстное:** открыт пресет → пишет пресет (у безымянного спросит имя); открыт чат → снимок чата. Двойной клик по пресету открывает его голый граф. Дефолт-стенд стартует **чистым** (Персонаж/Лорбук/Режиссёр без демо). **Отложено:** «модель в файл чата» (Вариант 1: новый чат без модели, ключ остаётся глобально в `rlm-store.json`) — согласовано отложить.
Альтернативы: старый выпадающий ☰-менеджер (Р-21) — заменён полноэкранным меню с пресетами.

## Р-24. Перевод: провайдеры без ключей (как в ST) + один нейро-коннектор
Перевод в полях нод и в чате управляется нодой `Транслитер`. Провайдеры **Google/Yandex/Bing — без ключей** (взято из ST `translate.js`: они используют бесплатные эндпоинты; Alibaba в ST нет — заменён на Bing). Серверный роут `/api/rlm/translate` (до CSRF). **Нейро**-перевод (LLM) — через **один** коннектор `in:neuro` (виден, если хоть один режим = «Нейро»): решено «не усложнять — одна машина переводит в обе стороны». «Разные машины» достигаются выбором **провайдера на режим** (напр. предпросмотр Google, замена Нейро). Кнопки на полях: **RU** предпросмотр EN→RU (обратимо), **EN** замена RU→EN. Записи `Души` тоже редактируемы + переводимы (сохранение `/doc-save`, удаление `/doc-del`).
Альтернативы: две отдельные нейро-пары API/Опции (по одной на направление) — отвергнуто как избыточное.

## Р-25. `Хроника` — авто-память в лорбук чата (система A, референс MachineMechanic)
Новая нода `Хроника`: сцена диалога → модель сжимает в запись `{заголовок, текст, ключи}` → в **лорбук чата** (архив по ключам, нумерованные главы). Это **система A** плагина `MachineMechanic`/MemoryBooks — **отдельная от `Души`** (та = динамичная MD-память, система C «Дневник души»). Обе «память», но разной природы: `Хроника` = структурный архив сцен по ключам в лорбуке; `Душа` = MD+RAG. Связь с чатом — **сервис-порт «Хроника»** на ноде `Чат` (как «Последнее сообщение»), не общий выход. **Приоритет бюджета:** ручные (человек) записи лорбука ВСЕГДА важнее авто-глав `Хроники` — сортировка «не-`mm` → `mm`» (правилом, без магии с числами order). № главы = **макс+1** (не «количество» — иначе коллизия при удалении средней); `order`=№ (свежее важнее при бюджете). **`ignoreBudget`:** авто у Хроники — нет; **ручной пин** — да (галочка «Всегда в промт (мимо бюджета)» в редакторе записи). **MemoryBooks не трогаем** — работаем только с форком `MachineMechanic` (референс — `backend-research.md`, разбор всех опций).
**Отложено (в `plan-lorebook-vector.md` → «Открытые вопросы»):** (1) имитация ST-outlet через мульти-выход лорбука (per-entry адрес); (2) развязка `order` на два ключа (бюджет vs позиция в блоке) — пока один рычаг; (3) ST-рекурсия лорбука пакетом (`preventRecursion`/`delayUntilRecursion` + потолок глубины).
Альтернативы: слить `Хронику` с `Душой` в один UI — отвергнуто (разная природа памяти); давать `ignoreBudget` авто-главам — отвергнуто (раздует блок, убьёт бюджет).

## Р-26. Вид ноды в чате = второй живой экземпляр на ОБЩИХ данных (не двигать ноду, не дублировать код)
Цель — **мобильный сценарий**: во время игры пользователь сидит в **чате** и НЕ ходит на холст нод. Значит нужные ноды (у кого есть вижн: `Лорбук`/`Режиссёр`/`Душа`/…) открываются **прямо из чата**. Принцип «нода↔вижн»: нода = живая копия своего вижна; **вижн — только глазком** (не зумом). Глазок на самой ноде (холст) → её вижн **полноэкранным оверлеем**. Открытое **из чата** (значком) → вид ноды **ВНУТРИ контейнера чата** (нода чата → над `.chat-stage`; вижн чата → над `#immersive`), НЕ на весь экран.
**Как строим (ключевое):** нода на холсте **стоит на месте**; в чате — **второй ЖИВОЙ экземпляр** тем же билдером (`buildLorebookNode`) на **тех же данных** (`view._entries = master._entries`, общий по ссылке). Так: (а) **один код** — правим билдер один раз, копии UI нет; (б) **одни данные** — оригинал и вид не расходятся, правки не делаем дважды. Ровно модель «чат-нода ↔ полноэкранный чат» (два iframe одного `chat.html`, одни данные). Вид исключён из графа (снят класс `node-lore`; `serializeGraph` берёт только `:scope > .node` у `#world`). Общий массив держим **in-place** (`splice`/`push`), крутилки ноды досинхроняются на закрытие.
Альтернативы: **переносить саму ноду** в оверлей чата — отвергнуто как костыль (нода уезжает с холста, провода дёргаются, два интерфейса склеиваются). **Отдельная копия UI/данных** для чата — отвергнуто (двойные правки, расхождение).

## Р-27. Групповой чат Telegram = мультиплеер: живые люди — отдельные персонажи, «кто есть кто» — розеткой на участника
В режиме «Группа» нода `Telegram` показывает **панель активных участников**; каждый пишущий — отдельный персонаж ролеплея. Привязка «человек играет за героя» задаётся **проводом**: у каждого участника свой **вход-порт** у левой кромки ноды, туда тянут `Персонаж`/`Персона`, и описание уходит в промт системной заметкой (`tgBuildCastNote`). Тема форума: бот может **читать и отвечать только в одной выбранной теме** (`message_thread_id`), выбор — прямо в ноде (список виденных тем + «🔒 текущая»).
Почему: в духе RLM «розетка = видимая ручка» — «кто есть кто» задаётся видимым проводом, а не спрятанной настройкой; технически связь участник↔персонаж сериализуется **бесплатно** штатными `portKey`/`findPort` (порт-обёртка `svc-in[data-in="cast:<id>"]`). Живой участник = свой персонаж = «мультиплеер для ролеплея».
Альтернативы: (а) выпадашка «Персона» на участника — отверг (не граф, прячет связь); (б) одна общая персона на всех — не мультиплеер.

## Р-28. Заглушка участника («Не подмешивать») = ПОЛНЫЙ игнор
Заглушённый участник: реплики **не пишутся в историю**, **не идут в промт и память**, и **не будят бота** (даже @упоминанием/reply). В логе он остаётся **виден, но серым** (🔇) — визуальный контроль; тумблер **«скрыть вне контекста»** прячет его из лога совсем.
Почему: полу-заглушка (только вырезать из контекста) — дырявая: заглушённый всё равно мог разбудить бота @упоминанием и оставался в записи. «Заглушить» должно означать «человека для ИИ нет вовсе», при этом ведущий видит, что тот пишет (серым) — отсюда лог виден по умолчанию, а скрытие опционально.
Альтернативы: (а) только фильтр контекста — отверг (дырявая, будит бота); (б) прятать из лога сразу — отверг (пользователь хочет видеть серым, скрытие — по кнопке).

## Р-29. Один слушатель на токен: «Запустить» перехватывает опрос
Telegram разрешает лишь **один `getUpdates` на токен** (иначе 409 Conflict «terminated by other getUpdates»). Кнопка «Запустить» перед стартом **перехватывает** (`tgTakeover`): гасит другие ноды `Telegram` с тем же токеном в приложении, шлёт `deleteWebhook(drop_pending_updates)`, затем несколько раз `getUpdates` — «последний выигрывает», это выбивает **залипший** чужой опрос (закрытая вкладка/старый старт). Против **живого** второго экземпляра (другое окно/копия/сервер) не борется — показывает честную ошибку, не притворяясь, что слушает.
Почему: типовые причины Conflict (вебхук, дубль-нода, зависший опрос) должны сниматься сами на «Запуск», без ручных «останови того, подожди 30 сек».
Альтернативы: (а) ручные пляски — неудобно; (б) авто-ретейк в самом цикле опроса — отверг (с живым вторым это бесконечный пинг-понг).

## Р-30. Хранилище — сервер как ЕДИНСТВЕННЫЙ источник (модель SillyTavern), одна сессия (пересматривает Р-15)
Всё состояние (персонажи/пресеты/чаты/логи/графы/настройки/ключ API/оформление) живёт **только в серверной базе** `rlm-store` (файл на ключ). Клиент держит зеркало в памяти (`db`), грузит его с сервера по ключам при старте (тяжёлые снимки чатов — лениво при открытии), читает из `db`, а на каждую правку **пишет на сервер**. `localStorage` **не используется вообще** — ни как хранилище, ни как зеркало/фолбэк, ни для миграции. Нет связи → честный экран «нет связи», а не старые данные.
Почему: прежняя схема (сервер + дубль в `localStorage` + откат на него + миграция + отдельный файловый `store` под ключ) была лоскутной — и именно тихий откат на устаревший `localStorage` показывал телефону «старую» сессию. Одна серверная база = **одна сессия** на ПК/телефон/Termux по-настоящему, как у ST (тонкий клиент, сервер — авторитет). Сервер у нас всегда рядом: на ПК его поднимает приложение, в Termux он локальный, браузер по LAN к нему коннектится.
Альтернативы: (а) оставить localStorage-зеркало «на всякий» — отверг (это и был источник рассинхрона); (б) грузить всю базу монолитом — отверг (телефон давится ~16 МБ; грузим по ключам, тяжёлые графы чатов — лениво). Следствие (принято сознательно): без живого сервера офлайна нет — но он всегда есть.

## Р-31. Мобильное приложение (PWA) — держим просто по http как ST; настоящий app = secure context (Termux/https), отложено
Веб-версию «как приложение» на телефоне делаем **минимально, один в один как SillyTavern**: `app/manifest.json` (`display: standalone`) + apple-мета + иконки, **без service worker, без HTTPS, без тоннеля**. По http это даёт: iOS — запуск без адресной строки (apple-мета), Android — просто ярлык.
Почему именно так и почему настоящего приложения на Android по http НЕТ: **это правило браузера, а не манифеста/кода.** Chrome ставит настоящий устанавливаемый PWA (плашка «Установить», полный экран) только в **secure context = HTTPS ИЛИ `localhost`/`127.0.0.1`**. Телефон→ПК по сети (`http://192.168.x.x`) — ни то, ни другое. **ST у пользователя ставится приложением, потому что запущен в Termux НА телефоне и открыт как `http://localhost` — а localhost браузер считает безопасным.** Значит настоящий app-on-phone у RLM — это **Termux на телефоне** (localhost, как ST — совпадает с целью проекта Р-1/Р-4) либо тоннель/HTTPS для связки «телефон↔ПК». **Решено отложить до Termux** (пользователь: «термукс это на будущее»).

## Р-32. Групповой чат: «коробка передач» (слоты) + ранжиратор в чате

Групповой чат RLM = **«коробка передач»** (своё, нет ни в ST, ни в SoW): не отдельная групповая машинерия, а **N соло-игр** — у каждой карточки полный риг; активный «на передаче» = полная карточка, остальные = **«фантом»** (сжатое публичное впечатление, генерит **Рассказчик** на старте, читая карточку+лорбук; секреты не тащит).
- **Слот = ТИП ПЛАШКИ** комплитера (текст/маркер/**слот**), коннекторы ВНУТРИ (свёрнут = один разъём, раскрыт = вход у каждого поля). **Душа/Состояние — НЕ в слоте**, а отдельной **in-chat КОПИЕЙ слота** (та же id/имя, впрыск на глубину). Имя слота = имя карточки, авто-переименование.
- **Нарратор = слот** с флажком «Рассказчик»: всевидящий (на его передаче ВСЕ карточки полные — доступ ко всем), память = общий **Мир** (без Психики/Дневника/Статуса), без Фантома. Он же **СУДЬЯ**.
- **Ранжиратор = переключатель коробки передач**, живёт **В ЧАТЕ** (принцип «управление в чате, ноды = данные»; см. Р-26/кочерга-двигатель). Решает «кто следующий» дешёвым запросом (**фантомы + короткая история**, комплитер в «ранжирование»-режиме); **счётчики ходов** (3 поинта/перс до рассказчика, рассказчик сбрасывает на указанное число). **Бутстрап** = первый переход КОНСТАНТА (игрок написал → ранжиратор сам). *Отвергнут вариант «ранжиратор = лёгкий режим рассказчика в коробке передач» — мигал бы коробкой и мешал управление с данными.*
- **Двухканальная память:** личное (Психика/Дневник/Статус/Состояние) свапается со слотом; общий мир = Душа рассказчика, **в промт персонажей НЕ идёт** (иначе метагейм) — персонажи знают мир только из истории чата.
- **Что у SoW не берём:** русский хардкод маркеров, мёртвый лорбук сцены, утечку памяти сцены в соло.
- Полный план, детали и **чек-поинт реализации** — `plan-group-chat.md`.
Альтернативы (пробовали в сессии 2026-08-22, отвергнуты): (а) **HTTPS сервера с локальным CA** (`ssl.enabled`, сертификат с SAN на LAN-IP, установка CA на телефон) — откатили: возня с сертификатом на телефоне лишняя, телефон не пошёл на https-адрес; (б) **тоннель Cloudflare** (готовый доверенный https без возни на телефоне — то, что советует и дока ST) — не подняли: авто-защита среды блокирует скачивание/запуск сетевых бинарников, у самого ST встроенного тоннеля тоже нет; (в) `display: browser` / service worker / манипуляции с манифестом — тупик, т.к. корень не в манифесте, а в адресе (secure context). Урок зафиксирован в память [[rlm-pwa-keep-simple]]: не усложнять раньше времени, повторять как в ST.

## Р-33. «Программный DRY» — эмуляция сэмплера анти-повтора КОДОМ (для облака), выход веерный

Против «модель повторяет одни и те же фразы» на облачном API, где сэмплеров нет (см. Р-11: DRY/XTC живут только в Text Completion): делаем **отдельную ноду `Программный DRY`**, которая собирает список заезженных фраз **чистым кодом** (ноль запросов к модели) из последних ответов ИИ и просит модель их не повторять. Три механизма: авто-детект повторов из истории (n-граммы) + **два ручных банка** (штампы / анти-повторы) + **свежесть** (общая приписка). Смотрит только ответы ИИ (не реплики игрока).
- **Служебка — только английская** (инвариант [[rlm-prompts-english]]): обёртка и **промт свежести** по-английски; **банки ПУСТЫ по умолчанию** (русские дефолты убраны — иначе утекали бы в промт), содержимое наполняет пользователь под свой язык РП.
- **Два банка, а не один** (выбор пользователя): «штампы» и «анти-повторы» ведут себя одинаково (ловят фразу при появлении, `dryBankMatches`), но подаются модели разными секциями. Авто-детект повторов — отдельно.
- **Выход веерный — пользователь решает проводом:** та же нода → плашка комплитера (влияет на модель) И/ИЛИ **разъём «Анти-повтор» ноды `Критик`** (критик заворачивает ответ за повтор, `criticDryData`) И/ИЛИ оба. Так один инструмент покрывает «мягко (в промт)» и «жёстко (перекат критиком)».
- **Проводка иная, чем у Цели/Состояния:** на `Чат` нода НЕ висит — историю берёт сам `assembleMessages`; в промт попадает у любой плашки, подключённой к `.node-dry` (не по имени плашки).
Почему код, а не сэмплер: облачный Chat API не принимает DRY/XTC; «программный DRY» = единственный способ на облаке. Дёшево (без лишних вызовов), детерминированно, полностью под контролем.
Альтернативы: (а) **один банк** — отверг пользователь (хотел раздельно штампы/повторы); (б) **авто-подмешивание к Критику** без провода — отверг в пользу явного разъёма (пользователь сам решает, куда идёт список); (в) трогать телеграм-путь Критика (`tgCriticJudge`) — не стали (не фокус). Детали — `changelog.md`/`architecture.md`, память [[rlm-dry-antirepeat-state]].
